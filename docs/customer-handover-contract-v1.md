# Nova Shield customer handover contract v1

**Status: frozen at v1.** A change to this document is a new version, agreed
before either side implements against it.

This is the contract for the customer's report of accepted work, the scoped
access that lets them read it, the delivery of it, and the payment boundary.
It is a **companion to**, not a revision of,
`docs/completion-evidence-contract-v1.md` (v1),
`docs/dispatch-contract-v1.md` (v1),
`docs/daily-load-contract-v1.md` (v2.1),
`docs/operations-contract-v1.md` (v1.2) and
`docs/seasonal-sets-contract-v1.md` (v1.2). **No request shape, parameter,
error code or grant in any of those moved.** This batch is purely additive:
it adds tables, functions and one new settings key, and changes nothing that
existed.

**Nothing here has been applied to the live database.** Twenty-eight
migrations are pending, in filename order, and none has been applied
anywhere.

Defined by:

* `supabase/migrations/20261017090000_batch13_1_customer_reports.sql`
* `supabase/migrations/20261017100000_batch13_1_customer_access.sql`
* `supabase/migrations/20261017110000_batch13_1_report_delivery.sql`
* `supabase/migrations/20261017120000_batch13_1_payment_boundary.sql`

Proved by `tests/db/batch13-1.test.mjs` (127 checks) against a real
PostgreSQL and `tests/phase29.test.mjs` (38 checks) against the real admin
panel and the real customer page. **Deterministic fixtures:
`tests/fixtures/customer-handover-v1.json`**, ten scenarios, generated by
`npm run fixtures:handover` from this backend and verified byte-identical
across two clean rebuilds.

## 1. What this is, and the five things it is not

A **customer-facing report of accepted work**, a **capability** that opens
it, a **delivery** that reuses the existing outbound table, and a **payment
boundary that refuses**.

Five things it is **not**, each because the backend refuses it and a screen
implying otherwise would be lying:

| Not | Why it matters here |
|---|---|
| **A customer account platform** | No customer login, no password, no profile, no session. A capability is the whole authorisation. §4 |
| **A document manager** | The only customer-readable files are evidence records an owner explicitly published against one completion. Nothing else is reachable. §6 |
| **A sender** | A row in `notifications` is a message somebody still has to send. There is no worker in this repository and `sent` is never true on a queued row. §7 |
| **A payment system** | There is no invoice, no payment-received record and no `paid` state anywhere. Every payment request is `unavailable`. §9 |
| **Automatic anything** | No trigger, no scheduler, no "on completion" hook. Four deliberate acts, four buttons. §2 |

## 2. The four acts, and why they are four

| Act | Who | What it does NOT do |
|---|---|---|
| `set_evidence_publication` | owner | does not alter a document already issued |
| `generate_completion_report` | owner | does not publish, link or send |
| `publish_completion_report` | owner | does not issue a link or send |
| `deliver_completion_report` | owner | does not publish a draft |

Collapsing them into one "share report" button would collapse the first most
dangerously: an `access_hazard` photograph framing a key safe satisfies a
completion requirement under the evidence contract and must never reach a
customer. **The default is withheld**, and the owner's screen shows the
undecided count rather than letting silence pass for a decision.

## 3. The report

### 3.1 The source is an accepted completion, named

```
generate_completion_report(p_client_operation_id text, p_completion_id uuid)
  returns jsonb
```

**Owner-only** (`42501` otherwise). Refusals, in order:

| Condition | errcode |
|---|---|
| not the owner | `42501` |
| blank `client_operation_id` | `22023` |
| no such completion | `P0002` |
| the job's completion was reopened and not re-completed | `23514` |
| this completion is not the job's current one | `23514` |

The last two are different questions and `ns_job_completion_is_open()`
answers only the first — it is a **job**-level predicate, true again as soon
as a reopened job is completed a second time. The second is answered by the
row's own `supersedes_corrections` against the job's reopen count. A screen
generating from a stale completion hits the second, not the first.

### 3.2 Deduplication is logical, not by browser key

`client_operation_id` answers the retry nobody received a response to.
`source_version` answers the other half: a hash over the completion, its
correction count, its open state, the **published** evidence set (ids plus
captions), the recorded consumption and the approved commercial records. The
unique index is `(completion_id, source_version)`, so:

* the same key again → the stored receipt, `replayed: true`;
* a **fresh** key and the same facts → **the same report**, `replayed: true`;
* a fresh key after any of those facts changed → a **new version**.

### 3.3 A correction supersedes; it never rewrites

A new report names the one it replaces in `supersedes`, and the previous row
is stamped `publication_state: 'superseded'`, `superseded_at`. It keeps its
own frozen `document` for ever. A `before update` trigger refuses any change
to `id`, `job_id`, `completion_id`, `report_version`, `source_version`,
`document`, `generated_at` or `client_operation_id` (`23514`), and a `before
delete` trigger refuses deletion outright (`23514`).

### 3.4 The review hold is visible

`review_hold` is set at generation when frozen evidence has no publication
decision, and when the job has no accepted quote. It is **not** an error:
a report of the work is useful without photographs. `publish_completion_report`
clears it. Nothing pretends a held report went out.

### 3.5 The document: an allowlist, field by field

`ns_customer_report_document(uuid)` builds the whole projection by naming
every field. There is no `to_jsonb(row)` and no `select *` anywhere in it,
which is why a column added to some table next year cannot appear on a
customer's document by accident.

```json
{
  "document_kind": "completion_report", "document_version": 1,
  "company":  { "state": "configured", "name": "…", "phone": "…", "email": "…" },
  "customer": { "customer_id": "…", "name": "…" },
  "property": { "address_line1": "…", "city": "…" },
  "job":      { "job_id": "…" },
  "completion": {
    "completion_id": "…",
    "accepted_at": "…",              // the SERVER's own time
    "work_finished_at": "…",         // the CREW's claim, or null
    "work_finished_state": "reported" | "unknown",
    "reported_work_time_state": "reported_by_crew" | "unknown"
  },
  "work": [ { "description": "…", "service": "…" } ],
  "evidence": [ {
    "evidence_id": "…", "requirement": "after", "caption": "…",
    "capture_time_state": "device_reported" | "unknown" | "unreliable",
    "captured_at": "…" | null,
    "location_state": "device_reported" | "unavailable" | "denied" | "unknown",
    "verification": "device_reported_not_server_verified",
    "received_at": "…"
  } ],
  "evidence_withheld_count": 1,
  "materials": [ {
    "material": "…", "quantity": 2.5 | null, "level": "part" | null,
    "unit": "litre", "measurement_state": "exact" | "estimated" | "level_observed"
  } ],
  "materials_note": "Reported for your records. Materials are not charged …",
  "commercials": { … §8 }
}
```

**The company block is the existing `company` settings row**, returned whole,
so the report and the quote page cannot disagree about who sent them.

### 3.6 What is deliberately absent, and why

| Absent | Why |
|---|---|
| `ns_property_access.access_code`, `.internal_note` | a key and an office note. 12.1 grants no column-level read for either. |
| `properties.access_note`, `.hazard_note`, `.parking_note` | crew working detail; a hazard note is often **about** the customer. |
| `ns_job_completions.note`, correction reasons, exception reasons | internal narrative. An exception records that we accepted a completion *without* something. |
| `ns_job_evidence.captured_lat/_lon/_accuracy_m` | the original GPS metadata. The document says whether location was reported; it hands over no coordinates. |
| material costs, `ns_stock_operations`, reservations | what a thing cost us is never on a customer's document. |
| `job_attachments.caption` | the **internal** caption. Only `ns_evidence_publications.customer_caption` reaches a customer. |
| any other customer's anything | the projection is built from one job and names one customer. |
| seasonal set identity and rental history | a company-owned Christmas set stays a rental. The document never names a set's previous property or season, and never implies installation transferred ownership. |

### 3.7 Device claims are never server facts

`accepted_at` and `work_finished_at` are separate fields with separate
meanings, and `work_finished_state: 'unknown'` does **not** borrow the
acceptance time. Every evidence entry carries
`verification: 'device_reported_not_server_verified'` — a watermark is pixels
a client drew and a GPS reading is what a phone said.

### 3.8 Materials are reported, never costed

Units and precision travel with the figure. A level-tracked supply has **no
quantity** and reports `level` with `measurement_state: 'level_observed'`; an
estimate reports `estimated`. No rate, no extension, no total, and
`materials_note` says so in the customer's own words. Consumption reports do
not become invoice lines.

## 4. The capability

### 4.1 The mechanism, chosen and stated

A **cryptographically random capability**, stored only as a **SHA-256 hash**,
with a server-checked scope, a **required** expiry and a revocation that
takes effect on the next read.

* **Randomness**: two `gen_random_uuid()` values concatenated — 244 bits from
  PostgreSQL's own `pg_strong_random`. **pgcrypto is not assumed**: nothing
  in this repository's migrations uses it, so `gen_random_bytes` would be a
  deployment surprise. `sha256()` is built in since PostgreSQL 11.
* **At rest**: `token_hash` (64 hex) and `token_prefix` (first 8 characters,
  for support and audit). The raw token is returned **once**, by the issuing
  call, and is never stored, logged or recoverable.
* **Not** a customer login. There is no customer auth in this project, and
  inventing one is a platform, not a batch. **Not** an email or customer-id
  match, which is a guess dressed as authorisation.

### 4.2 Scope

```
issue_customer_grant(p_client_operation_id text, p_scope text,
                     p_report_id uuid default null,
                     p_customer_id uuid default null,
                     p_expires_at timestamptz default null,
                     p_label text default null) returns jsonb
```

| scope | opens | requires |
|---|---|---|
| `report` | exactly one report | `p_report_id`, and the report must be **published** (`23514` otherwise) |
| `customer_collection` | that customer's **published** reports | `p_customer_id`, and refuses `p_report_id` (`22023`) |

**There is no path from a single-report token to the collection.** A report
token calling `list_customer_documents` gets its own one document. A grant
issued against a customer who is not the document's own is refused (`22023`).

**Owner-only.** A crew cannot mint customer access.

### 4.3 Expiry is the owner's policy, not a default

`expires_at` is **required**. With `app_settings.customer_portal.link_expiry_days`
set, a null `p_expires_at` uses it (`expiry_source: 'settings_policy'`);
without it, a null is refused (`22023`, "There is no default"). An expiry in
the past is refused. How long a customer may reach their own paperwork is a
business decision with a real cost either way, and burying a 30-day guess in
a migration would hide it.

### 4.4 The token is shown once

The issuing call returns `token` and `token_state: 'shown_once'`. A **replay**
under the same key returns the grant's identity with `token: null` and
`token_state: 'not_recoverable'` — the server keeps no copy, so a replay
cannot hand one back. A lost token is re-issued as a new grant. No function
reads a token back, and no screen offers to.

### 4.5 Revocation, with its residual stated

```
revoke_customer_grant(p_client_operation_id text, p_grant_id uuid, p_reason text)
```

Owner-only, reason required (`22023`). The receipt says exactly what it does:

| field | value |
|---|---|
| `stops_new_reads` | `true` |
| `stops_new_document_tickets` | `true` |
| `already_issued_signed_urls` | `"remain valid for the rest of their own lifetime"` |

A signed Storage URL cannot be recalled, so the contract states the residual
rather than promising an instant cut-off. The ticket TTL (§6) bounds it to
**120 seconds**. Revocation does not delete the report: what was issued stays
on record.

## 5. The customer's read

```
get_customer_report(p_token text, p_report_id uuid default null) returns jsonb
list_customer_documents(p_token text) returns jsonb
```

**Anon-callable, deliberately** — the capability is the authorisation, the
same deliberate decision the Batch 7.1 inventory records for
`get_customer_quote` and `respond_to_quote`. Those two keep their existing
anon grants; this batch asserts it.

**Neither ever raises for a bad token.** A typed envelope with a `state`,
because a page has to render "this link has expired" rather than a stack
trace, and because a raise and a return are distinguishable from outside in a
way that tells a guesser which tokens exist.

| state | meaning |
|---|---|
| `ok` | the frozen document, with `report_id`, `report_version`, `issued_at`, `document`, `documents` |
| `superseded` | the document **plus** a message that a corrected version exists. The customer still sees what they were sent. |
| `expired` | the window has passed |
| `revoked` | withdrawn |
| `unavailable` | the report is still a draft. Never the word "draft". |
| `out_of_scope` | a report grant aimed at another document |
| `not_found` | not on this link — **the same words** for another customer's real report and for an invented id |
| `unknown` | no such capability |

Every attempt is logged in `ns_customer_grant_reads`: grant id, 8-character
prefix, what was asked for and the outcome. **No token and no hash**, because
an audit log is read by more people than the table it audits. An unknown
token is recorded with a null grant id, so a sweep of guesses is visible.

The document returned is the **frozen** one. This read never re-projects.

## 6. Files: a ticket, never a path

```
request_customer_document(p_token text, p_report_id uuid, p_evidence_id uuid)
  returns jsonb      -- anon-callable, typed envelope
redeem_document_ticket(p_ticket_id uuid) returns jsonb   -- SERVICE ROLE ONLY
```

Four checks, in order, and the last is the one a naive implementation forgets:
the capability is valid, it covers this report, the report is a customer
document, and **the evidence is listed in the frozen document**. Checking the
publication table as it stands today would let a decision made after issue
change what an issued document can open.

A customer never receives a storage path. An authorised reader gets a
**single-use, 120-second ticket**; only a service-role worker can exchange it
for a signed URL, bounded by `max_signed_seconds: 120`.

**The TTL is a technical bound, not a business policy.** 120 seconds is a
click-to-fetch round trip; "how long may a customer keep their paperwork" is
`customer_portal.link_expiry_days` and belongs to the owner.

| answer | when |
|---|---|
| `{state: 'ok', ticket_id, expires_at, signed_url: null, signing_state: 'requires_worker'}` | authorised |
| `{state: 'not_found'}` | out of scope, **or** not published — identical answers |
| `{state: 'file_missing'}` | the record is there, the object is not |
| `{state: 'expired' / 'revoked' / 'unknown'}` | the capability |

**THE WORKER DOES NOT EXIST IN THIS REPOSITORY.** `supabase/functions` holds
`submit-request` only. Real Storage signing is therefore **UNRUN**, and the
customer page says "we will email this photograph to you" rather than
pretending a download is ready.

A note from building this: 11.1 freezes an accepted completion's evidence
rows, so the dangling-evidence branch of `request_customer_document` is
defence rather than the reachable case. The case that **does** happen is a
row whose storage object is gone, and `redeem_document_ticket` answers it
with `file_missing` rather than a path to guess with.

## 7. Delivery

```
deliver_completion_report(p_client_operation_id text, p_report_id uuid,
                          p_channel text default 'sms',
                          p_expires_at timestamptz default null) returns jsonb
record_report_delivery_outcome(p_delivery_id uuid, p_delivery_state text,
                               p_provider_message_id text default null,
                               p_provider_error text default null) returns jsonb
report_deliveries(p_report_id uuid) returns jsonb
report_delivery_timing(p_report_id uuid) returns jsonb
ns_inbound_reply_support() returns jsonb
```

### 7.1 The existing pipeline, reused

The outbound queue is the **existing `notifications` table** (Batch 2/5), and
the five delivery states are **12.1 §8's**, with the same meanings, so a
reader who learnt them on the dispatch screen does not learn them again. No
second sender, no second pipeline, no trigger and no scheduler.

| state | meaning |
|---|---|
| `accepted` | recorded and **queued**. NOT sent. |
| `delivered` | the provider says it went |
| `provider_failed` | the provider says it did not — reason required (`22023`) |
| `unknown` | we asked and do not know. **Not a success.** |
| `unavailable` | no provider configured, or no contact on file — reason required |

`unavailable` is a **receipt, not an exception** (the owner needs it on the
screen), and it **mints no capability**: a link nobody can be sent is a live
credential with no reader. The CHECK
`(delivery_state = 'unavailable') = (notification_id is null)` makes that a
database rule.

### 7.2 One live delivery per report

A partial unique index on `(report_id) where delivery_state in ('accepted',
'unknown')`. A second live delivery is `23505`. A finished one (delivered,
failed, unavailable) does not block a later deliberate re-send. `unknown`
**keeps blocking** and `resolved_at` stays null, because the provider may have
neither idempotency nor an outcome lookup and a retry might be the customer's
second identical text. Clearing it is a human decision, recorded **under the
original key** — the row is updated, never replaced, so one logical delivery
stays one.

### 7.3 The recipient is resolved, never supplied

From the report's job's customer. `deliver_completion_report` takes no
recipient parameter, and the suite asserts that from
`pg_get_function_arguments`. The receipt reports `recipient_known: true|false`
and never reads the address back.

### 7.4 The token and the one place it rests

`deliver_completion_report` mints the capability and queues the message **in
one transaction**, so the token never travels back through a browser. It
exists at rest in exactly one place: the `notifications.payload.link_path`
that is about to send it, which is what an outbox is. It is **not** in the
receipt, **not** in `ns_report_deliveries`, **not** in
`ns_handover_operations` and **not** in `ns_customer_grant_reads`. The suite
sweeps every text and jsonb column in `public` for the raw token and permits
exactly that one exclusion, by name.

The payload carries the customer's name, the report id and version, and the
link. **No access code, no internal note, no materials and no totals** — the
document is behind the capability, and a payload is stored, replayed and
rendered in places a document is not.

### 7.5 The five clocks, and the two-minute question

`report_delivery_timing` reports them separately because they fail for
different reasons and only some are ours:

| clock | meaning |
|---|---|
| `accepted_at` | the **server's** acceptance of the completion. Where the clock starts — not an offline gesture. |
| `readiness_at` | when the report became a customer document (publication). Null while a review holds it. |
| `report_generated_at` | when this document was built |
| `enqueued_at` | when the message was queued. **Local processing ends here.** |
| `resolved_at` | the provider's answer. **Delivery ends here**, and only an adapter sets it. |

Derived: `acceptance_to_readiness_seconds`, `local_processing_seconds`
(ours), `provider_seconds` (theirs).

`sla_state`: `met` (acceptance → provider outcome ≤ 120s), `missed`,
`failed`, `awaiting_provider`, or **`indeterminate` whenever the provider is
unavailable or the outcome is unknown**. An unavailable provider cannot meet a
delivery target, and scoring it `met` would be measuring our own INSERT.
`sla_basis` says so in the row.

### 7.6 The worker is missing, and that is reported

This repository contains no notification worker and no Edge Function source
for one. **Real sending is UNRUN.** What is implemented and tested is the
local contract — what is queued, in what shape, with what states and
timestamps — plus `record_report_delivery_outcome` as the adapter's way back
in, driven in tests by a **double**. No inserted row is ever described as
processed.

### 7.7 Inbound replies: the extension point only

`ns_inbound_reply_support()` returns `state: 'unconfigured'`,
`inbound_contract: 'none'`, the reasons, and the extension point. **No webhook
route, no signature scheme, no phone-identity proof and no reply state
machine is invented** — all four are provider-specific, and a pipeline built
against a guess is a pipeline rewritten the day a provider is chosen.

The one rule recorded now so a later implementation inherits it: **an
automatic reply never discloses an access code**, an internal note or a
hazard note. 12.1 keeps those ungranted at column level for exactly this
reason, and an auto-responder texting the gate code to whoever messaged the
business number would undo it in one line.

## 8. The commercial record on the document

`ns_job_approved_commercials(uuid)`:

```json
{
  "accepted_quote": { "quote_id": "…", "version": 1, "total": 480 } | null,
  "approved_changes": [ { "change_order_id": "…", "description": "…", "amount": 120 } ],
  "approved_total": 600 | null,
  "currency": "CAD" | null,
  "currency_state": "from_accepted_quote" | "from_settings" | "unconfigured",
  "commercial_state": "accepted_quote" | "no_accepted_quote"
}
```

Two sources, both already authoritative and already frozen: the **accepted**
quote (Batch 5 froze its customer-facing content and total at send;
acceptance is the customer's own act) and **approved** change orders (11.1
prices them in the same transaction as the approval, so an approved one
always has a figure).

**A proposed change order is not here.** It is a crew's suggestion, it has no
price by construction, and putting it on a customer's document would turn a
proposal into a charge.

**No accepted quote means no total at all** — `approved_total: null`, not a
zero. Currency comes from the accepted quote's own frozen column first, the
`quote_defaults.currency` setting second, and `unconfigured` third. Batch 5's
`coalesce(…, 'CAD')` is deliberately **not** repeated: on a customer-facing
document a guessed currency beside a real figure is worse than none.

Pricing stays in the backend. This batch alters no quote, total, tax,
minimum, grant or status, and the migration asserts `ns_quotes` has grown no
`paid`, `paid_at` or `payment_status` column.

## 9. The payment boundary, and the dependency it names

```
ns_payment_provider() returns text
ns_payment_balance(p_job_id uuid) returns jsonb
create_payment_request(p_client_operation_id text, p_job_id uuid,
                       p_expected_amount numeric default null) returns jsonb
job_payment_state(p_job_id uuid) returns jsonb
```

### 9.1 What the existing model has, and what it does not

Searched for by name, not assumed: `ns_quotes` (status, version, total,
currency) and `ns_change_orders` (owner-priced approved amounts). **There is
no invoice table, no payment table, no ledger of money received and no `paid`
state anywhere in this system.**

So **a remaining balance is not established**, and this is the dependency
rather than something to invent:

| field | value |
|---|---|
| `approved_total` | the accepted quote plus approved change orders |
| `amount_settled` | **null** — not recorded anywhere |
| `remaining_balance` | **null** — and never the approved total renamed |
| `balance_state` | `no_accepted_quote` / `no_settlement_model` / `established` |
| `missing_dependency` | the sentence naming what is absent |

Three things it would have been wrong to do: derive an amount from material
quantities (consumption is not a price and 11.1's point is that completion
prices nothing); derive it from a report total (a report is a document);
or call the approved total "outstanding" (approved is what was agreed;
outstanding is agreed **minus received**, and the second half does not exist).

`ns_payment_balance` **introspects** for `public.ns_payments(job_id, amount,
state)` and binds to it if it ever exists — a hook for a model that does not
exist, not a claim that it does, and not a schema this batch creates. A table
of that name with a different shape reports `no_settlement_model` rather than
guessing its columns. The payment scenario in the fixtures and test J5 prove
the binding with a **labelled double** created and dropped by the test.

### 9.2 Unconfigured means unavailable

`app_settings.payments.provider` unset → every request is
`state: 'unavailable'` with a reason. **No real payment link, credential,
sandbox account, provider SDK or webhook assumption**, and `checkout_url`
stays null: a URL comes from a provider's API and a fabricated one is a link
that takes money nowhere.

A `prepared` request binds the **remaining balance** (not the approved
total), the currency and the provider, under CHECKs that make an
`unavailable` request bind nothing and a `prepared` one bind all three.
`p_expected_amount` is the figure the owner was shown; a stale one is refused
(`23514`), the same shape as 10.1's confirmation lock. The bound amount is
part of the intent fingerprint, so the same key with a different figure is
`23505`.

Every receipt carries `paid: false`, `is_payment: false` and the sentence
"Preparing or opening a payment request is not payment."

### 9.3 Provider work still outstanding

Carried in `job_payment_state.remaining_provider_work` as data, not only in
this document, so nobody wires a provider and calls it done:

1. a **settlement model**: what was invoiced, what was received, and when;
2. **server-side verification** of the provider's own confirmation (a signed
   webhook or an authoritative API read) — never a browser redirect;
3. **idempotent reconciliation** from the provider's reference back to the
   approved commercial record;
4. **refund, chargeback and partial-payment** semantics;
5. the **fee and tax treatment** of a provider's charges, which this system
   does not model.

## 10. Operations, keys and replay

`ns_handover_operations` is this batch's replay ledger — a separate table from
`ns_dispatch_operations`, because widening another batch's `kind` CHECK would
make a 12.1 assertion fail for a 13.1 reason. Same discipline, and the **same
hash function** (`ns_load_intent_fingerprint`), because two intent hashes that
disagree is a bug waiting to happen.

`ns_handover_replay_guard(key, kind, scope_id, fingerprint)` refuses in this
order — **kind, then scope, then intent**:

| mismatch | errcode |
|---|---|
| a key first used for another kind | `23505` |
| the same kind, a different scope | `23505` |
| the same scope, a different payload | `23505` |

Scope before intent is deliberate (and is 12.1's ordering): a caller who may
not see the report a key was spent on must learn that, not that its payload
differs from one it cannot read.

Kinds: `evidence_publication`, `report_generation`, `report_publication`,
`grant_issue`, `grant_revoke`, `report_delivery`, `payment_request`.

## 11. Grants, stated exactly

| object | anon | authenticated | service_role |
|---|---|---|---|
| `get_customer_report`, `list_customer_documents`, `request_customer_document` | **execute** | execute | execute |
| `redeem_document_ticket` | — | — | **execute only** |
| every other 13.1 function | — | execute | execute |
| `ns_customer_grants` | — | **— (no select at all)** | all |
| `ns_completion_reports`, `ns_evidence_publications`, `ns_handover_operations`, `ns_customer_grant_reads`, `ns_document_access_tickets`, `ns_report_deliveries`, `ns_payment_requests` | — | select | all |

`ns_customer_grants` is the one table this batch adds with **no
`authenticated` select**: it carries token hashes, and a hash plus a known
token format is an offline guessing target. The owner's view is
`customer_grants()`, which returns prefixes only.

`redeem_document_ticket` returns a storage path, so `authenticated` must not
have it either: an admin reading a file goes through the admin paths, not
through a customer's ticket.

Asserted with `has_table_privilege` / `has_function_privilege` /
`has_column_privilege` in the migrations, and exercised with **real
`set role`** in the suite — the table owner bypasses grants, so a privilege
test that does not change role proves nothing.

## 12. What 13.2 and later own, and what they must not assume

* **No route registration.** `admin/js/components/customer-handover.js` is
  standalone-mountable and tested that way; no `admin/js/main.js` edit and no
  global `admin.css` change. That is the integration change.
* **No worker.** The sending adapter and the document-signing worker are both
  absent, and both are named as UNRUN rather than stubbed into looking
  present.
* **No customer auth.** If a later batch wants customer accounts, that is a
  platform decision and this contract's capability is not a prototype of one.
* **No offline anything.** Every mutation here requires a connection and a
  server-checked state.
* **No invented settlement model.** §9 is the dependency; filling it is a
  batch, not a patch.
