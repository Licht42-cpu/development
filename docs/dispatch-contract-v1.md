# Nova Shield dispatch contract v1.1

**Status: frozen at v1.1.** A change to this document is a new version,
agreed before either side implements against it.

> **v1.1 (Batch 15.1) — additive, plus one rule given a name.**
>
> **§2a The crew-scope rule, once.** `ns_can_work_job(uuid)` is unchanged in
> behaviour, but it and 11.1's `can_work_job(uuid)` now both read
> `ns_job_is_mine(uuid)`, so they cannot drift again. The reason is readable
> as text through `ns_job_crew_scope(uuid)` → `owner`,
> `assigned_to_my_vehicle`, `unassigned_single_vehicle`,
> `unassigned_needs_a_claim`, `assigned_elsewhere`, `not_admin`,
> `no_such_job`, and through the admin read `job_crew_scope(uuid)` which
> adds `is_mine`, `claimable`, `active_vehicles` and a message.
>
> **§2b The crew's claim.**
> `claim_job_for_vehicle(p_client_operation_id text, p_job_id uuid,
> p_reason text default null, p_expected_revision integer default null)`
> — admin, crew-callable. "This job is on MY car." It cannot take a job off
> another car (`42501`), cannot claim for another car (the vehicle is
> resolved from the caller's crew record and is not a parameter), cannot
> unassign, and moves no stock. Claiming what is already yours answers
> `{no_op: true}` and does **not** move the day's revision. Otherwise it is
> an assignment: same invalidation, same revisions, same key ledger
> (`kind = 'assignment'`), with `how: 'claimed'` on the receipt.
>
> **`assign_job_to_vehicle` is unchanged** — same signature, same owner-only
> gate. Both doors now call one internal core, so they cannot drift. Its
> receipt gains one additive field, `how: 'assigned' | 'claimed'`.
>
> **`ns_can_see_property(uuid)`** now reads the same rule through the job.
> Scope is unchanged for one vehicle; with two, a property whose job is on no
> car is not readable until somebody claims or assigns it.

## 1. What this is, and the four things it is not

An **ordered day per vehicle**, for one crew and at most two. Manual
reordering, reassignment and rescheduling; the equipment two cars are
fighting over; property access instructions and defined work zones; the
crew's reports of what went wrong; and two deliberate customer messages.

Four things it is **not**, each because the backend refuses them and a
screen that implied otherwise would be lying:

| Not | Why it matters here |
|---|---|
| **Routing or optimisation** | No travel time, no distance, no sequencing suggestion. The order is the owner's, by hand. |
| **A stock movement** | Reassigning or rescheduling re-plans both cars' loads and transfers **nothing**. Every receipt says `stock_moved: false`. |
| **A completion** | `work_finished` is the crew downing tools. An accepted completion is `complete_job_with_evidence` (completion contract §4) and nothing else. §7 |
| **An automatic message** | Nothing sends on opening a screen, on a route change or on a location reading. There is no trigger and no scheduler in these migrations. §8 |

## 2. What is reused rather than rebuilt

A second source of truth for "which car is this job on" is how a job gets
dispatched twice, so there isn't one:

| Already existed | Still the authority for |
|---|---|
| `ns_job_vehicle_assignments` (10.1) | **which car a job is on.** Keyed by `job_id`, so one job on two cars is structurally impossible. Asserted, not assumed (`batch12-1` C2). |
| `ns_vehicle_day_jobs(location, date)` (10.1, 12.1 round two) | **which visits are "today"**, including the one-vehicle default and the two-vehicle "belongs to neither". |
| `ns_unassigned_day_jobs(date)` (10.1) | **what needs a car.** |
| `ns_work_day_bounds(date)` (10.1 v2.1 §2a) | **the operating day.** Dispatch and load cannot disagree about it. |
| `ns_load_intent_fingerprint(jsonb)` (10.1 corrective) | **intent hashing.** One hash function, one behaviour. |
| `properties.access_note` | **the entrance note.** Not duplicated; read from where it lives. §6 |
| `notifications` (Batch 2/5) | **the outbound message row.** §8 queues into it rather than building a second pipeline. |
| the five seasonal RPCs (9.1) | **installation, recovery, inspection, release and renewal.** §9 reads their state and invokes none of them. |

## 3. `get_dispatch_day` — the one supported read

```
get_dispatch_day(p_location_code text, p_work_date date) returns jsonb
```

**Any admin**, scoped: a vehicle the caller cannot see raises `42501`, an
unknown code raises `P0002`. Reading **writes nothing** — the day's version
row is created by a mutation, not by a look.

```json
{
  "location_id": "…", "location_code": "car_a", "location_name": "Car A",
  "work_date": "2027-08-02",

  "work_day_timezone": "America/Edmonton" | null,
  "work_day_timezone_state": "configured" | "unconfigured",
  "window_starts_at": "2027-08-02T06:00:00+00:00",
  "window_ends_at":   "2027-08-03T06:00:00+00:00",

  "revision": 3,
  "can_plan": true,

  "stops": [ { …§4… } ],
  "unassigned_jobs": [
    { "job_id": "…", "scheduled_for": "…", "status": "scheduled",
      "customer_name": "…", "property_id": "…" }
  ],
  "readable_vehicles": [ { "location_id": "…", "code": "car_a", "name": "Car A" } ],

  "load_plan": {
    "state": "current" | "confirmed" | "superseded" | "closed" | "none",
    "plan_id": "…", "revision": 2,
    "invalidated_at": "…" | null,
    "invalidated_reason": "a job was assigned to car_b" | null,
    "needs_rebuild": true
  }
}
```

| field | type | null? | meaning |
|---|---|---|---|
| `revision` | integer | no | The day's dispatch version. **1** when nobody has edited it, so a first edit has something true to quote. Every accepted mutation bumps it. |
| `can_plan` | boolean | no | `is_owner()`. A crew reads its day and reports on it; ordering, reassigning and rescheduling are the owner's. |
| `work_day_timezone_state` | text | no | Same two values the load contract publishes. `unconfigured` means UTC, which can put a late-afternoon visit on the next day's list — **a screen must say so.** |
| `load_plan.needs_rebuild` | boolean | no | A fact about the plan, not an instruction this function carried out. §5 |
| `load_plan.state` | text | no | `none` when no plan exists for the day. An invalidated live plan reads `superseded`; the read deliberately returns it rather than "none", because that is exactly the day that needs saying something about. |

## 4. A stop

```json
{
  "job_id": "…",
  "position": 1 | null,
  "order_state": "explicit" | "derived" | "stale",
  "assigned": true,
  "scheduled_for": "…" | null,
  "status": "scheduled",
  "customer_id": "…", "customer_name": "…",
  "property_id": "…" | null
}
```

**`order_state` is three answers, not two.**

* `explicit` — somebody set this position for this car on this date.
  `position` is 1-based and dense.
* `derived` — nobody has ordered the day; the stops are in `scheduled_for`
  order, timeless work last, and `position` is **null**. The read says the
  order is a consequence rather than implying a choice.
* `stale` — a position exists but was set for a different car or a
  different date. It is **not applied** and **not silently deleted**:
  saying "stale" is the honest answer. A reassignment or a cross-day
  reschedule drops the row rather than carrying it across.

**`assigned` false** means unassigned and therefore this car's by the
one-vehicle rule. With two vehicles an unassigned job appears in
`unassigned_jobs` on **both** screens and in neither `stops`.

## 5. The three planning mutations

All three are **owner-only** (`42501` otherwise), take a
`p_client_operation_id`, and are replay-safe per operation (§11).

```
reorder_dispatch_day(p_client_operation_id text,
                     p_location_code       text,
                     p_work_date           date,
                     p_job_ids             uuid[],
                     p_expected_revision   integer) returns jsonb

assign_job_to_vehicle(p_client_operation_id text,
                      p_job_id              uuid,
                      p_location_code       text,          -- null REMOVES
                      p_expected_revision   integer default null,
                      p_reason              text default null) returns jsonb

reschedule_job(p_client_operation_id text,
               p_job_id              uuid,
               p_scheduled_for       timestamptz,
               p_expected_revision   integer default null,
               p_reason              text default null) returns jsonb
```

### What each does to the load plan

| Mutation | Effect on the load | Why |
|---|---|---|
| `reorder_dispatch_day` | **none**, and the receipt says so in `load_effect` | The load is a WHOLE-DAY decision (load contract §2): the same tools are wanted whatever order the stops are visited in. |
| `assign_job_to_vehicle` | invalidates the plan on **both** the car it left and the one it joined, for that job's day | Each car's whole-day needs just changed. |
| `reschedule_job` | invalidates the plan for that job's vehicle on **both** the day it left and the day it joined | Same reason, across days. |

**Invalidation preserves history.** A `current` plan becomes `superseded`
and is stamped `invalidated_at` / `invalidated_reason`. A `confirmed` plan
**keeps its status and its transfer receipts** — it is the record of what
the crew agreed to load — and is stamped as well, which is what makes a
late confirmation refusable. Nothing is rebuilt implicitly: `build_load_plan`
is owner-only and creates a revision, and doing it inside a reassignment
would hide a new recommendation behind an unrelated action. The read
reports `needs_rebuild` and the owner presses the button. **Rebuilding
posts no stock movement** (load contract §1).

### Refusals

| code | when |
|---|---|
| `42501` | not the owner; or a vehicle the caller cannot see |
| `22023` | blank operation key; an empty or duplicated `p_job_ids`; a null `p_scheduled_for` (clearing a schedule is not a reschedule); a location that is not a vehicle |
| `23514` | a stale `p_expected_revision`, **with the current number in the message**; an order that leaves out or adds a job; a job with no `scheduled_for` (it is on no day yet) |
| `23505` | the key was used for a different operation kind, or for a different intent (§11) |
| `P0002` | no such job, plan or location code |

### Receipts

`reorder_dispatch_day` → `{ location_id, location_code, work_date,
revision, ordered, replayed, load_plans_invalidated: [], load_effect,
stops: [{job_id, position, order_state}] }`

`assign_job_to_vehicle` → `{ job_id, work_date, from_location_id,
to_location_id, to_location_code, reason, replayed,
load_plans_invalidated: [{plan_id, location_id, work_date, revision,
status_now}], stock_moved: false, revisions: {from, to} }`

`reschedule_job` → `{ job_id, scheduled_for, previous_scheduled_for,
work_date_before, work_date_after, work_day_timezone, location_id, reason,
replayed, load_plans_invalidated: […], stock_moved: false }`

## 6. Property instructions, and what a UI filter is not

```
get_property_access(p_property_id uuid) returns jsonb        -- any admin, scoped
set_property_access(p_client_operation_id, p_property_id,
                    p_entrance_note, p_hazard_note, p_parking_note,
                    p_internal_note, p_access_code, p_customer_note,
                    p_expected_version integer default null) -- OWNER ONLY
```

`properties.access_note` is **not duplicated**: it is returned as
`access_note` from where it already lives, and the field console already
reads it through `getJob`. What this adds is what that column cannot hold.

| field | audience |
|---|---|
| `entrance_note`, `hazard_note`, `parking_note` | the crew going there. Separate columns because they are separate sentences. |
| `internal_note`, `access_code` | **ours.** No column-level `SELECT` exists for `authenticated` at all. |
| `customer_note` | **the only customer-facing field**, and the only thing in `ns_property_customer_notes`. |

**AUTHORISATION IS NOT A UI FILTER.** The two private columns are served by
`get_property_access()` and nothing else. It allows the owner, or a crew
whose vehicle has work at that property **on any date** (a crew preparing
tomorrow needs tonight's gate code). A crew with no work there gets `42501`
through the function, the table and every view in these migrations. The
grant is issued the only way that works in PostgreSQL — `revoke` the table
`SELECT`, then `grant` the columns — because a column `REVOKE` against a
table-level grant does nothing at all.

**The receipt never echoes the code.** It reports `has_access_code`,
`has_internal_note` and `has_customer_note`: whether one is on record is a
different fact from what it is, and a receipt is logged, replayed and
rendered.

**Coordinates.** `coordinates` is `{state: "known"|"missing", lat, lng}`.
Missing stays missing: no default pin, no city centre, no guessed entrance.

### Work zones

```
save_property_work_zone(p_client_operation_id, p_property_id, p_label,
                        p_kind, p_space, p_points jsonb,
                        p_image_source text default null,
                        p_note text default null,
                        p_zone_id uuid default null,
                        p_expected_version integer default null)  -- OWNER ONLY
retire_property_work_zone(p_client_operation_id, p_zone_id, p_reason)  -- OWNER ONLY
```

`kind` ∈ `work_area | hazard | parking | access_path`.
`space` ∈ `geographic | image`, **declared, not guessed**:

* `geographic` — `[{lat, lng}, …]`, real coordinates in range, so it can go
  on a map.
* `image` — `[{x, y}, …]` as **0..1 fractions of `image_source`**, which is
  required: a drawing on a photo is meaningless without saying which photo.
  Fractions rather than pixels so they scale to whatever size it is drawn.

**Three points minimum** — two points are a line. Validated by a CHECK
constraint, so a bad drawing is refused by the database and not only by the
screen that drew it (`22023` from the function, `23514` from the
constraint).

**A ZONE IS NOT A SURVEY AND NOT A GEOFENCE.** `source` is
`owner_drawn` and the CHECK permits no other value, so the data cannot
claim to be surveyed. Nothing in this system triggers on entering a zone.
Retiring keeps the row with `retired_at`, `retired_by` and
`retired_reason`: what was drawn, and when it stopped applying, is history.

**A keyboard-only path exists and is the primary one.**
`admin/js/components/property-access.js` edits the points as number
inputs with Add and Remove buttons; there is no drag handle and no canvas.
The map and photo canvas are 12.2's, and this contract is complete without
one.

## 7. The five states that must never merge

```
report_job_issue(p_client_operation_id, p_job_id, p_kind, p_reason,
                 p_material_id uuid default null)       -- owner or that car's crew
resolve_job_issue(p_client_operation_id, p_issue_id,
                  p_resolution_state, p_note)           -- OWNER ONLY
set_dispatch_stage(p_client_operation_id, p_job_id, p_state,
                   p_reason text default null,
                   p_expected_version integer default null)
```

| state | who says it | where it lives |
|---|---|---|
| **cancelled** | the office, commercially | `ns_jobs.status` |
| **skipped** | the owner | `ns_job_dispatch_state` (owner-only) |
| **blocked** | the crew: went, could not get in | `ns_job_dispatch_state` |
| **work_finished** | the crew: tools down at the property | `ns_job_dispatch_state` |
| **accepted_completed** | **the server**, with evidence | `ns_job_completions` (11.1) |

`ns_job_dispatch_status` reports `job_status`, `dispatch_state`,
`completion_state` and `open_issue_count` **side by side**, from 11.1's own
helper rather than a re-derivation. Reading `work_finished` as completed is
the mistake this view exists to prevent, and `set_dispatch_stage` cannot
produce a completion: its receipt carries `is_completion: false` and the
current `completion_state`. **11.1's gate is intact** — a direct
`update ns_jobs set status='completed'` is still refused (`42501`,
"call complete_job_with_evidence"), asserted by this batch's migration and
by `batch12-1` G4.

`kind` ∈ `blocked_access | equipment_breakdown`. A **blocked-access** report
also sets the stop to `blocked`, because that is literally what the crew is
saying. A **breakdown** does not: a broken washer does not necessarily stop
the visit, and deciding that is the owner's. Both are visible either way,
and `material_id` is null for a tool that is not in the catalogue —
reported as unknown rather than guessed.

An issue **never** changes the job's commercial status and never completes
or cancels anything; the receipts say so in `job_status_changed` and
`completion_recorded`. `resolution_state` ∈ `open | resolved |
work_rescheduled | work_cancelled`, is reasoned, and is recorded **once**
(`P0002` on a second attempt). `work_cancelled` records that the owner
decided so; the commercial status is still changed on the job itself, where
the quote guards can see it.

## 8. The two customer messages, and five outcomes

```
request_job_notification(p_client_operation_id, p_job_id, p_kind,
                         p_channel text default 'sms')   -- owner or that car's crew
record_notification_outcome(p_request_id, p_delivery_state,
                            p_provider_message_id, p_provider_error) -- OWNER ONLY
job_notification_requests(p_job_id) returns jsonb
```

`kind` ∈ `on_the_way | access_request`. **Deliberate only**: nothing calls
these on opening a screen, on a route change or on a location reading.

| `delivery_state` | means | a send? |
|---|---|---|
| `accepted` | recorded, and a row queued in `notifications` | queued, **not sent** |
| `delivered` | the provider says it went | yes |
| `provider_failed` | the provider says it did not, with its reason | no |
| `unknown` | we asked and do not know | **NOT success** |
| `unavailable` | no SMS provider configured, **or** no number on file | no, and nothing was queued |

The two `unavailable` reasons are told apart in `reason`, because they are
fixed by different people in different places. An `unavailable` request is
**not an exception**: the crew needs it on the screen, and the receipt's
`delivery_state` is the honest answer. `sent` is always `false` in the
receipt — queueing is not sending.

**The recipient is resolved from the JOB's customer**, never from a
caller-supplied address, and is never read back: the reads report
`recipient_known` and `authenticated` has no column grant for `recipient`.
**No message payload carries an access code** — asserted in the fixtures
(`payload_has_a_code: false` for every queued row).

**One live request per job per kind.** Two "on the way" texts for one visit
is `23505`. A `delivered`, `provider_failed` or `unavailable` request does
not block a later deliberate one.

**THE HONEST RETRY RULE**, because the provider may have neither
idempotency nor an outcome lookup:

* `delivered` and `provider_failed` are terminal (`23514` on a second
  outcome).
* **`unknown` stays live and keeps blocking a second request**, because a
  retry might be the customer's second identical text. Clearing it is a
  human decision: record `delivered` (we believe it arrived) or
  `provider_failed` (we believe it did not), and say why.
* A crew cannot record an outcome at all (`42501`). It does not get to mark
  its own message delivered.

`notifications.sent_at` and `status` are set only when somebody records
`delivered`. **SMS provider configuration stays external**: the provider
name is read from `app_settings.notifications ->> 'sms_provider'` and
nothing in these migrations configures, contacts or assumes one. Every
outcome in the fixtures and the suites comes from a **double**.

## 9. Equipment conflicts and seasonal stages

```
dispatch_equipment_conflicts(p_work_date date) returns jsonb   -- any admin
ns_vehicle_day_equipment(p_location_id uuid, p_work_date date) -- the derivation
```

**A read.** Looking transfers, reserves, buys and consumes nothing.

Requirements are **whole-day**: a washer wanted at three stops on one car is
one requirement, not three. Items are ordered by material name, so two
reads agree.

| `conflict` | meaning |
|---|---|
| `shared_scarce` | both cars need it and there is not enough to go round |
| `unavailable` | nothing usable at Base or on either car |
| `damaged_only` | what we have is in the damaged pool |
| `location_unknown` | the ledger has one, but not at Base or on a car |
| `missing_data` | nothing records how many we have |
| `none` | no conflict; the row is still returned |

**Unknown is never zero.** `ns_material_stock_by_location` cross-joins every
material with every location and coalesces to 0, so "nothing recorded" is
read from `last_move_at is null` and reported as `null`. A level-tracked
item has no number at all and reports `level_state` instead.

`ns_dispatch_seasonal_work` reports, per job: the assignment's status, the
set's physical status and location, `promised_to_a_customer`,
`aboard_a_vehicle`, `physically_installed`, and a `stage` **label**
(`to_install | to_recover | to_inspect | finished | cancelled |
needs_review`). The label is for a screen: **moving a dispatch stage invokes
none of the five seasonal acts**, which keep their own RPCs. A commercial
assignment never implies the set is aboard a car, and company-owned lights
never become the customer's property.

## 10. Winter work, with no invented rule

```
ns_winter_automation_state() returns jsonb                  -- any admin
ns_winter_dispatch_candidates(p_work_date date) returns jsonb
dispatch_winter_visit(p_client_operation_id, p_job_id, p_location_code,
                      p_scheduled_for, p_reason)            -- OWNER ONLY
```

`mode` is `owner_triggered`. The snowfall threshold, the forecast source and
the visit allowance are each reported as **`unconfigured`**; none is
invented, and no salt dosage appears anywhere. The owner's `p_reason` is
required and is the record of the decision a weather rule would otherwise
have made.

`ns_winter_dispatch_candidates` returns **one row per property** with every
winter service on it. Walkway and deck variants are one visit to one place,
and `dispatch_winter_visit` refuses a second winter visit to the same
property on the same day (`23505`) — one trip out cannot become two
dispatches and two minimums. It **creates no job and no minimum**
(`created_job: false`, `created_minimum: false`) and reuses
`reschedule_job` and `assign_job_to_vehicle`, so the invalidation, the
revision checks and the key ledger behave exactly as they do elsewhere.

### Compatibility: exactly what changed outside this contract

**One additive change and one new refusal, both in the load contract's
surface and neither altering a signature:**

1. `ns_load_plan_result` — and therefore `build_load_plan`,
   `get_load_plan().plan` and every load receipt — gains
   **`invalidated_at`** and **`invalidated_reason`**. Additive; nothing is
   removed or renamed, and a client that ignores them behaves as before.
2. `confirm_load_plan` gains a **fourth refusal case**: a plan whose day has
   been re-planned since it was built is refused with `23514` and a sentence
   naming the reason. The signature, the parameters and the response fields
   are unchanged. Recovery is the same shape as the other three: re-read,
   rebuild (owner), confirm the new revision.

Everything else is new tables, new views and new functions. No existing
grant was narrowed, and `properties`, `customers`, `ns_jobs` and
`notifications` keep every column and policy they had — 12.1 adds rows and
reads, never a rewrite.

## 11. Retries, and what a key means

Every mutation in this contract records its key, its intent fingerprint and
the receipt it returned, in **`ns_dispatch_operations`**. The guard is the
same one the load and seasonal contracts use, in the same order:

**kind → scope → intent.** Scope before intent, so a caller who cannot see
the location learns nothing about what the key was used for.

| situation | outcome |
|---|---|
| same key, same intent | the stored receipt, with `replayed: true`. No second edit, no second revision, no second message. |
| same key, different intent | `23505`, "that key was used for a different …" |
| same key, different operation kind | `23505`, "a key belongs to the operation it was first used for" |
| same key, a location the caller cannot see | `42501`, and nothing about the key is disclosed |

`p_job_ids` in a reorder is **not sorted** before hashing: the order *is*
the intent there, unlike a closing count where two orders are the same
request.

| `set_dispatch_stage` (`skipped`, `planned`), `resolve_job_issue` | yes | `42501` | `42501` | no execute |
| `request_job_notification` | yes | yes | `42501` | no execute |
| `record_notification_outcome`, `dispatch_winter_visit` | yes | `42501` | `42501` | no execute |

Every 12.1 table is RLS-enabled with exactly one read policy, and
`authenticated` holds **no insert, update or delete** on any of them: every
write goes through a function that checks who is asking, bumps the version
and records the key. Asserted with `has_table_privilege` and
`has_column_privilege` rather than by attempting a write, because the table
owner bypasses grants and a successful attempt would prove nothing.

## 14. What 12.2 owns, and what it must not assume

Codex owns the field map, the navigation handoff, offline rendering of
coordinates and zones, the crew's issue and arrival actions, and the Maps
SDK decision. This contract supplies the data and the authorisation; it
deliberately does **not** decide:

* **No basemap or imagery promise.** Nothing here caches, licenses or
  implies a map provider, and no map dependency is added to any package
  file.
* **No geofence.** A zone is a drawing. Nothing triggers on entering one,
  and GPS proximity is not arrival — 12.2's own acceptance says so.
* **No arrival state.** `work_finished` and `blocked` are deliberate crew
  reports; an "arrived" state is 12.2's to define if it needs one, and it
  cannot be inferred from a location reading here.
* **No offline writes.** Every mutation in this contract requires a
  connection and a server-checked version. Whether any of them earns a
  queued type is 12.2's decision under its own contract, not an assumption
  this document makes.
